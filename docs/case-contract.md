# The case contract

A case is a directory `cases/<domain>/<slug>/` that a human can run by hand and
that the harness can judge. `python3 harness/bench.py validate` enforces every
rule below. A case that violates them does not enter the corpus.

## Files

```
cases/<domain>/<slug>/
  case.json        required: metadata, ground truth, per-tool expectations
  composer.json    required: the case must be installable and runnable on its own
  src/             required: the fixture
  runtime/check.php optional: executes the fixture and proves the ground truth
  phpstan.neon     optional: only if the case needs a specific level or rules
  psalm.xml        optional: only if the case needs a specific error level
  mago.toml        optional: only if the case needs specific rules
  vendor/          generated by the harness, never committed
```

## case.json

```json
{
  "id": "narrowing/is-int-on-string",
  "title": "is_int() on a string parameter guards an unreachable branch",
  "domain": "narrowing",
  "rule_class": "impossible-condition",
  "php": { "min": "7.4", "max": null },
  "targets": ["src"],
  "config": { "phpstan": { "level": 9 } },
  "ground_truth": {
    "basis": "runtime_proof",
    "statement": "is_int() is false for every string, so the branch is dead.",
    "runtime_script": "runtime/check.php",
    "citation": "https://www.php.net/manual/en/function.is-int.php"
  },
  "expect": {
    "phpstan": {
      "mode": "diagnostics",
      "required": [{ "code": "function.impossibleType", "line": 15, "message_regex": "always evaluate to false" }],
      "allowed": [{ "code": "deadCode.unreachable", "reason": "same root cause, correct report" }]
    },
    "psalm": { "mode": "diagnostics", "required": [{ "code": "TypeDoesNotContainType", "line": 15 }] },
    "mago": { "mode": "clean" }
  },
  "notes": "Free-text context for a human reader."
}
```

### Field rules

* `id` must equal the directory path under `cases/` and match `<domain>/<slug>`.
* Optional `criterion_id` identifies a semantic rule as `<domain>/<semantic-rule>`
  in the same domain. It defaults to `id`. Multiple fixtures of that rule share
  one criterion ID, so parameter variants cannot inflate the coverage target.
  Matching IDs catch declared duplicates; independent review must catch two
  differently named fixtures testing the same fact.
* Optional `source_candidate_id` links a clean-room fixture to a lead in
  `factory/catalog.json`. The lead does not establish the fixture's ground truth.
* `domain` groups cases in the report. Use an existing domain when it fits:
  `narrowing`, `assignability`, `callables`, `generics`, `nullability`,
  `legacy-patterns`, `phpdoc-extensions`, `dead-code`, `enums`, `arrays`.
* `rule_class` names the analyzer rule class under test, in the vocabulary of the
  tools (`impossible-condition`, `argument.type`, `unused-method`, `mixed-return`)
  rather than a made-up label.
* `php.min` / `php.max` gate the case when a syntax requires a version.

### Ground truth

`ground_truth.basis` is one of `runtime_proof`, `php_semantics`, `upstream_test`,
`upstream_docs`, `maintainer_statement`.

The validator rejects a case whose basis is a citation without a `citation`, or a
`runtime_proof` without a `runtime_script`.

**The ground truth must be established from the language, the runtime, or the
tool's own documented promise - never from what one analyzer happens to print.**
"PHPStan reports X here" is not a ground truth; it is a measurement.

Prefer `runtime_proof`. A fixture with a `runtime/check.php` that exits 0 when
the code behaves as stated is worth more than three paragraphs of argument.

### Expectations

Each tool gets exactly one entry. Modes:

| mode | meaning |
| --- | --- |
| `clean` | the tool must report nothing for this fixture |
| `diagnostics` | `required` must be reported, `forbidden` must not, everything else is counted unless listed under `allowed` |
| `unsupported` | the tool does not implement this rule class by design; needs `reason` and `citation` |

Predicates (`required`, `forbidden`, `allowed`) match on `code` (string or list,
compared case-insensitively), `message_regex`, `file` (suffix match) and `line`
(± `line_tolerance`). A predicate matches only when every field it sets matches.

Use `line_tolerance` (e.g. `line_tolerance: 1` or `2`) instead of maintaining differing
target lines per tool when docblock syntax errors or parser diagnostics attach to
different lines across tools (e.g. docblock comment line vs. following declaration line).
`line_tolerance` is reserved for docblock/parser diagnostic location differences to keep
declared expectations symmetrical across tools; do not use it to soften semantic checks.

In fixtures where `mode: clean` is expected, multiple cascading follow-up diagnostics
stemming from an unrecognized inference (for example, both a missing closure parameter
type and a mixed return statement) are not collapsed into a single diagnostic claim.
Because benchmark accounting evaluates one binary verdict per case (`false_positive`),
the case is counted once without suppressing the tool's actual output.

An expectation may carry its own `basis` and `citation`. Use that when the
fixture was harvested from one tool's test suite: that tool is judged against its
own documented expectation (`"basis": "upstream_test"`, with the test file as the
citation) while the other two are judged against the case's neutral ground truth.
Without this, a fixture taken from PHPStan's suite would judge PHPStan against
itself.

Predicates must be **specific**: a `code` or a distinctive `message_regex`. An
empty predicate matches every diagnostic and is rejected by the validator.

`allowed` entries need a `reason`, because acknowledging output is a judgement
that a reviewer must be able to audit. If a tool's report is correct but not what
the case tests, acknowledge it; if it is wrong, leave it unacknowledged so it
counts as a false positive.

## Style for fixtures

* Minimal. One fixture should demonstrate one rule class. Extra code invites
  unrelated diagnostics that have to be acknowledged for no reason.
* No dependencies unless the rule class requires them (`composer.install: true`
  then, and the case must stay installable).
* No `@psalm-*` / `@phpstan-*` annotations unless the case is explicitly about
  those extensions. If it is, the other tools get `mode: unsupported` with a
  citation - they are not expected to read a competitor's annotations.
* Deterministic: no time, no randomness, no network.

## How a case gets written

1. Find a pattern where analyzers disagree, or where one disagrees with the
   language. Seed candidates are tracked in `factory/catalog.json`.
2. Write the fixture and a `runtime/check.php` if the behaviour can be executed.
3. Write `case.json` with your expectation, then run
   `python3 harness/bench.py run --case <id>` and read the actual verdicts.
4. Reconcile: either your expectation was wrong (fix it, and say so in `notes`),
   or the tool is wrong (leave the verdict as is - that is the finding), or the
   tool cannot implement it (record `unsupported` with the citation).
5. `python3 harness/bench.py validate` must pass, and the case must not break
   any existing case.
